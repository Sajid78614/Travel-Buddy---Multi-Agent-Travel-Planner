## 1. What is LangGraph?

**LangGraph** is a framework for building **stateful AI workflows and agent systems** using a graph-based architecture.

A LangGraph application is mainly built around:

- **State** — shared data that moves through the workflow
- **Nodes** — functions/agents that perform work
- **Edges** — connections that determine execution order
- **Reducers** — rules for combining state updates
- **Graph** — the complete workflow
- **Checkpointer** — persists graph state/checkpoints
- **Thread ID** — identifies a particular conversation/session
- **Invoke** — executes the compiled graph

A simple mental model is:

```text
STATE
  │
  ▼
START → NODE → NODE → NODE → END
          │      │      │
          └── Update ───┘
               STATE
```

## 2. Travel Agent Project Architecture

Our travel planning system contains four specialized nodes/agents:

1. **Flight Agent**
   - Searches for flights
   - Uses the `search_flights()` tool

2. **Hotel Agent**
   - Searches for hotel information
   - Uses Tavily search

3. **Itinerary Agent**
   - Takes the user request, flight results, and hotel results
   - Uses an LLM to generate a travel itinerary

4. **Final Response Agent**
   - Combines flights, hotels, and itinerary
   - Uses an LLM to generate the final response

The current workflow is:

```text
START
  │
  ▼
Flight Agent
  │
  ▼
Hotel Agent
  │
  ▼
Itinerary Agent
  │
  ▼
Final Agent
  │
  ▼
END
```

This is a **sequential LangGraph workflow**.

## 3. What is State?

State is one of the most important concepts in LangGraph.

The **State** represents the shared data available while the graph is executing.

Our project defines:

```python
class TravelState(TypedDict):
    messages: Annotated[list[AnyMessage], operator.add]
    user_query: str
    flight_results: str
    hotel_results: str
    itinerary: str
    llm_calls: int
```

Conceptually, the state can look like:

```python
{
    "user_query": "Plan a 5-day trip from Delhi to Dubai",

    "flight_results": "Emirates..., IndiGo...",

    "hotel_results": "Hotel A..., Hotel B...",

    "itinerary": "Day 1: Burj Khalifa...",

    "messages": [...],

    "llm_calls": 2
}
```

## 4. Why Do We Need State?

Different agents need information generated by previous agents.

For example:

```text
User
 │
 └── user_query
        │
        ▼
   Flight Agent
        │
        └── flight_results
                  │
                  ▼
             Hotel Agent
                  │
                  └── hotel_results
                            │
                            ▼
                      Itinerary Agent
```

The Itinerary Agent needs:

```text
user_query
flight_results
hotel_results
```

Instead of manually passing every variable between every function, LangGraph provides a **shared state**.

Every node receives the current state and can return updates to it.

## 5. State as a Backpack

A simple way to understand state is to imagine a **backpack being passed between agents**.

Initially:

```text
STATE

user_query = "Delhi to Dubai"
flight_results = ""
hotel_results = ""
itinerary = ""
```

The Flight Agent receives it and adds:

```text
flight_results = "Emirates..., IndiGo..."
```

Now:

```text
STATE

user_query = "Delhi to Dubai"
flight_results = "Emirates..., IndiGo..."
hotel_results = ""
itinerary = ""
```

The Hotel Agent receives the updated state and adds:

```text
hotel_results = "Hotel A..., Hotel B..."
```

Then the Itinerary Agent can access everything it needs.

Therefore:

> **State is the shared working memory of the graph during execution.**

## 6. `TypedDict` and the State Schema

We define:

```python
class TravelState(TypedDict):
```

`TypedDict` defines the expected structure of the state.

For example:

```python
user_query: str
```

means `user_query` should contain a string.

Similarly:

```python
flight_results: str
hotel_results: str
itinerary: str
```

define other state fields.

Our state structure is:

| Field | Purpose |
|---|---|
| `messages` | Stores conversation/agent messages |
| `user_query` | Original travel request |
| `flight_results` | Flight search results |
| `hotel_results` | Hotel search results |
| `itinerary` | Generated travel itinerary |
| `llm_calls` | Tracks LLM calls or workflow steps |

## 7. Understanding `messages`

The messages field is:

```python
messages: Annotated[list[AnyMessage], operator.add]
```

This is special because it uses a **Reducer**.

A reducer tells LangGraph how multiple state updates should be combined.

For messages, we want:

```text
Old Messages
+
New Messages
=
Combined Messages
```

Example:

```python
["User message"]
+
["Flight results fetched"]
```

becomes:

```python
[
    "User message",
    "Flight results fetched"
]
```

This is why we use:

```python
operator.add
```

Without this reducer, a new `messages` value could replace the previous value instead of accumulating messages.

---

## 8. Regular State Fields vs Reducer Fields

A normal state field such as:

```python
flight_results: str
```

is generally overwritten when a node returns a new value.

For example:

```python
return {
    "flight_results": flight_data
}
```

updates:

```text
flight_results
```

with the latest result.

But:

```python
messages: Annotated[list[AnyMessage], operator.add]
```

is accumulated.

Therefore:

```text
flight_results → Replace/update value

messages → Add new messages to existing messages
```

## 9. What is a Node?

A **node** is a function that performs one step of the workflow.

Example:

```python
def flight_agent(state: TravelState):
```

A node usually follows this pattern:

```text
Current State
     │
     ▼
    Node
     │
     ├── Read State
     ├── Perform Work
     └── Produce Result
             │
             ▼
       State Updates
```

In code:

```python
def some_node(state):
    data = state["some_field"]

    result = do_something(data)

    return {
        "another_field": result
    }
```

The important idea is:

> **Nodes receive state and return state updates.**

They do not have to return the entire state.

The node returns only the fields it wants to update:

```python

    "flight_results": flight_data,
```

## 19. What are Edges?

Nodes define **what can happen**.

Edges define **what happens next**.

Our edges are:

```python
graph.add_edge(START, "flight_agent")

graph.add_edge(
    "flight_agent",
    "hotel_agent"
)

graph.add_edge(
    "hotel_agent",
    "itinerary_agent"
)

graph.add_edge(
    "itinerary_agent",
    "final_agent"
)

graph.add_edge(
    "final_agent",
    END
)
```

Therefore execution is:

```text
START
  ↓
Flight Agent
  ↓
Hotel Agent
  ↓
Itinerary Agent
  ↓
Final Agent
  ↓
END
```

## 21. The Current Graph is Sequential

Our current architecture is:

```text
Flight
  ↓
Hotel
  ↓
Itinerary
  ↓
Final
```

Each node runs after the previous node.

This is called a **sequential workflow**.

However, flight and hotel searches are mostly independent.

A future version could potentially use a parallel structure:

```text
                  START
                    │
             ┌──────┴──────┐
             ▼             ▼
       Flight Agent    Hotel Agent
             │             │
             └──────┬──────┘
                    ▼
             Itinerary Agent
                    │
                    ▼
               Final Agent
                    │
                    ▼
                   END
```

This can improve efficiency because flight and hotel searches could run independently.

## 24. What is a Checkpointer?

The project creates:

```python
checkpointer = PostgresSaver(_conn)
```

A checkpointer allows LangGraph to persist graph checkpoints.

Without persistence:

```text
Run Graph
   ↓
State Exists
   ↓
Program Ends
```

With PostgreSQL checkpointing:

```text
LangGraph
    │
    │ Save checkpoints
    ▼
PostgreSQL
    │
    ├── State/checkpoint data
    ├── Thread information
    └── Metadata
```

This makes graph execution durable across multiple calls/process lifetimes, depending on how the application is used.

## 26. Thread ID

When invoking the graph, we provide:

```python
config = {
    "configurable": {
        "thread_id": "user_aarohi"
    }
}
```

A `thread_id` identifies a particular persistent graph thread/conversation.

For example:

```text
PostgreSQL
│
├── thread_001
│      └── checkpoints for conversation 1
│
├── thread_002
│      └── checkpoints for conversation 2
│
└── thread_003
       └── checkpoints for conversation 3
```

This prevents unrelated conversation threads from being treated as the same thread.

For a production application, thread IDs could look like:

```text
travel_session_001
travel_session_002
travel_session_003
```

rather than permanently hardcoding:

```text
user_aarohi
```

## 31. Getting Only the Final Response


is more appropriate when we only want the Final Agent's response.

## 33. `llm_calls` Observation

The current code increments:

```python
"llm_calls": state.get("llm_calls", 0) + 1
```

inside every agent.

However, the Flight Agent performs:

```python
search_flights(query)
```

and the Hotel Agent performs:

```python
tavily_search(query)
```

These are not necessarily LLM calls.

The obvious LLM calls occur when using:

```python
llm.invoke(...)
```

inside:

```text
Itinerary Agent
Final Agent
```

Therefore, if the field is supposed to count actual LLM calls, increment it only where `llm.invoke()` is called.

Otherwise, rename it to something like:

```python
agent_steps
```

or:

```python
workflow_steps
```

if the goal is to count executed nodes.

## 34. Checkpoint Persistence vs Long-Term Memory

It is important to distinguish:

```text
Checkpoint Persistence
```

from:

```text
Long-Term Semantic/User Memory
```

`PostgresSaver` provides persistent graph checkpointing associated with threads.

For example:

```text
thread_id = "travel_session_001"
             │
             ▼
        PostgreSQL
             │
             └── Saved graph checkpoints/state
```

But suppose we want the AI to remember long-term user preferences such as:

```text
User prefers vegetarian food
User prefers budget hotels
User's home airport is Delhi
User prefers window seats
```

and retrieve these preferences across different conversations.

That is a broader **long-term memory** problem.

A useful mental distinction is:

```text
                    MEMORY
                       │
            ┌──────────┴──────────┐
            │                     │
            ▼                     ▼
       Checkpoint             Long-Term
       Persistence              Memory
            │                     │
            ▼                     ▼
     Conversation/graph       Preferences,
       thread state          user facts,
                            cross-thread data
```

Therefore:

> `PostgresSaver` gives the project durable graph checkpoints, but it should not automatically be considered every possible form of long-term agent memory.
